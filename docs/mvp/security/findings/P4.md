## Проверено без находки

- **Път на временния файл за импорт** (`FinImportController::directory()`/`upload()`/`meta()`): съхранение в `storage_path('app/databackd-imports/<company_id>')` — **извън** `public/`, никога обслужвано директно по URL. Съхраненото име е винаги `<UUID>.<валидирано разширение>` (`Str::uuid()`, никога оригиналното клиентско име) — изключва path traversal/двойно разширение в пътя. `meta()` приема токен само ако минава `^[0-9a-f]{8}-[0-9a-f]{4}-...$` (строг UUID regex) — не може да се подаде `../`. Оригиналното клиентско име (`$meta['name']`) се пази само в сесия/`fin_import_batches.file_name`, никога в път на файл; показва се единствено с Blade `{{ $batch->file_name }}` (`resources/views/databackd/data/batches/show.blade.php:58`) — автоматично екраниран изход, не намерих `{!! !!}` върху него навсякъде в `resources/views/databackd/data/**`.
- **`pruneOldFiles()`** изтрива недовършени качвания над 2 дни; `ImportFinEntriesJob::deleteTempFile()`/`failed()` изтрива временния файл и при успешен, и при неуспешен импорт.
- **CSV кодиране**: BOM (`\xEF\xBB\xBF`) се маха, `mb_check_encoding`/`mb_convert_encoding` от Windows-1251, разделител (`,`/`;`/tab) се разпознава по най-честата поява на първия ред — прегледано, без находка извън DoS-лимита (P4-04, вече поправен).
- **XLSX/XLS автоматично разпознаване**: `readFile()` определя типа по магически байтове (`PK`→Xlsx, OLE подпис→Xls), никога по разширение, и никога не вика `IOFactory::load()`/auto-detect — изключва всички по-рискови PhpSpreadsheet readers (Gnumeric, ODS, Html, Xml), споменати в публичния advisory за PhpSpreadsheet 1.30.5.
- **Формули в качен Excel не се изпълняват при импорт**: `FinEntriesSheetImport` имплементира само `ToArray` (не `WithCalculatedFormulas`) → `Maatwebsite\Excel\Row::toArray()`/`Cell::getValue()` чете суровия текст на формулата (`$calculateFormulas=false` по подразбиране), никога `getCalculatedValue()` — качен `=WEBSERVICE(...)` в клетка не се изпълнява при четене/preview на импорта.
- **Zip Slip в PhpSpreadsheet Xlsx reader**: `vendor/phpoffice/phpspreadsheet/.../Reader/Xlsx.php` чете zip записи само с `ZipArchive::getFromName()`/`locateName()` — никъде `extractTo()` — не записва файлове извън паметта по зададено от архива име.
- **Content-Disposition filename injection** в генерираните имена на изтеглянията (`PnlReportController`, `CashflowReportController`, `CounterpartyReportController`, `ReportExportController`, `FinImportBatchController::errorsExport`): всички имена се градят само от Carbon `->format('Ymd')`/`->format('Y-m-d')`, преведени статични низове и строго whitelisted enum-и (`ReportBuilder::normalizeConfig()` → `rows`/`columns` само от фиксиран списък измерения; `CounterpartyData::normalizeSide()` → само `revenue\|expense\|all`) — никога суров потребителски текст; `batch`/`id` са `whereNumber`-ограничени route параметри. Няма CR/LF/кавичка от потребителски вход в тези заглавия.
- **`FinImportBatch` изолация между компании**: моделът ползва `HasCompany`/`CompanyScope` (P1 вече го е проверил динамично за цялото AFV дърво) — не намерих отделен пробив в моите файлове.
- **Качване на файлове за заявки за анализ — размер**: `CommentAnalysisRequest`/`DeliverableAnalysisRequest` ограничават `file`/`deliverable_file` до `max:20*1024` KB (20 MB) — непроменено, достатъчно.
- **Google Sheets / CSV-по-URL импорт** (`GoogleSheetsReader`, `routes/databackd/data-sources.php`): собственост на P5 — не е пипано и не е прегледано в дълбочина от мен.
- **Експортите без лимит на редове** (`FinEntriesExport` чрез `FromQuery`): потвърдих, че при голям брой записи заявката се изпълнява с chunking от самия `Maatwebsite\Excel` (`config/excel.php` → `chunk_size=1000`), така че паметта расте постепенно, не наведнъж; реалният лимит е времето на HTTP заявката (синхронна, без опашка за експорт) — отбелязано, но не е сменено (изисква UI промяна в чужд view за „експортът е голям, продължава във фонов режим“ — извън обхвата ми; кой **може** да експортира е проверка на права, P2).

## Рецепта за проверка

Всички стъпки по-долу са `php artisan tinker --execute="..."` на `databackd_local` (демо компания `company_id=4`) или еквивалентен малък PHP скрипт зареден със same bootstrap като `docs/mvp/tools/smoke.php`. Нищо от тях не оставя трайни промени (temp записи с маркер `S6-TMP-...` се изтриват; преименувани съществуващи записи се връщат към оригиналните си имена).

1. **dompdf `enable_php` никога не е включен в AFV (P4-01):**
   ```
   grep -rn "enable_php" app/Exports/Databackd/
   ```
   Очакван резултат: без съвпадения (или само в коментар, обясняващ защо не се ползва).

2. **CSV/Excel formula injection неутрализация (P4-03), за `FinEntriesExport`:**
   ```php
   $id = DB::table('fin_entries')->insertGetId(['company_id'=>4,'entity_id'=>1,'account_id'=>54,'entry_date'=>now()->toDateString(),'kind'=>'flow','amount'=>100,'currency'=>'EUR','amount_base'=>100,'counterparty_name'=>'=HYPERLINK("http://evil","x")','document_no'=>'S6-TMP-CHECK','source'=>'manual','created_at'=>now(),'updated_at'=>now()]);
   $row = DB::table('fin_entries')->join('fin_accounts','fin_accounts.id','fin_entries.account_id')->where('fin_entries.id',$id)->select('fin_entries.*','fin_accounts.code as account_code','fin_accounts.name as account_name','fin_accounts.type as account_type')->first();
   $cells = (new App\Exports\Databackd\Data\FinEntriesExport(request()))->map($row);
   echo $cells[13]; // очаква се "'=HYPERLINK(\"http://evil\",\"x\")" (с префикс ')
   DB::table('fin_entries')->where('id',$id)->delete();
   ```
   Очакван резултат: низът започва с `'` (апостроф), не с `=`.

3. **Import DoS лимит (P4-04):**
   ```php
   $importer = new App\Services\Databackd\Data\FinEntryImporter(4);
   $big = "a,b\n" . str_repeat("1,2\n", 50010);
   try { $importer->readCsvString($big); echo "FAIL: not rejected\n"; } catch (\Throwable $e) { echo "OK: " . $e->getMessage() . "\n"; }
   ```
   Очакван резултат: `OK: The uploaded file is too large...`.

4. **Файлове на заявки за анализ — извън `public/` (P4-02):**
   ```php
   $tmp = tempnam(sys_get_temp_dir(), 'x'); file_put_contents($tmp, "a,b\n1,2\n");
   $uploaded = new Illuminate\Http\UploadedFile($tmp, 'test.csv', 'text/csv', null, true);
   $stored = App\Models\Databackd\AnalysisRequest::storeUpload($uploaded);
   $publicPath = public_path('user-uploads/' . App\Models\Databackd\AnalysisRequest::FILE_FOLDER . '/' . $stored);
   echo "under public/: " . (file_exists($publicPath) ? "FAIL" : "OK (not public)") . "\n";
   echo "on private disk: " . (Storage::disk('databackd_private')->exists(App\Models\Databackd\AnalysisRequest::FILE_FOLDER . '/' . $stored) ? "OK" : "FAIL") . "\n";
   App\Models\Databackd\AnalysisRequest::deleteUpload($stored);
   ```
   Очакван резултат: „OK (not public)“ и „OK“.

5. **Разширения, забранени за заявки за анализ (P4-02):**
   ```php
   $tmp = tempnam(sys_get_temp_dir(), 'x') . '.svg'; file_put_contents($tmp, '<svg onload="alert(1)"></svg>');
   $uploaded = new Illuminate\Http\UploadedFile($tmp, 'evil.svg', 'image/svg+xml', null, true);
   try { App\Models\Databackd\AnalysisRequest::storeUpload($uploaded); echo "FAIL: accepted\n"; } catch (\Throwable $e) { echo "OK: " . $e->getMessage() . "\n"; }
   ```
   Очакван резултат: `OK: You are not allowed to upload files with extension: svg`.

## За S10

- **Съществуващите файлове на production под `public/user-uploads/databackd/analysis/*`** (и демо данните на S5 в тази среда) остават публично достъпни по предвидим URL, докато не се преместят физически на новия диск `databackd_private` (`storage/app/databackd/databackd/analysis/`) — препоръка: копиране на файловете (имената на `deliverable_file`/`analysis_request_comments.file` не се налага да се сменят, `AnalysisRequest::resolveDownload()` вече търси първо на новия диск). Допълнителна, по-бърза временна мярка (не съм я направил — засяга `public/**`, извън сигурно моите файлове): `.htaccess`-правило `Deny from all` конкретно за `public/user-uploads/databackd/analysis/`.
- **Мъртвият `<script type="text/php">` блок** в `resources/views/databackd/reports/export/pdf.blade.php:11-23` вече никога не се изпълнява (PivotPdf вече не включва `enable_php`), но остава в изгледа (чужд файл, S9) — препоръка: да се изтрие, за да не се „съживи“ случайно при бъдеща промяна, която пак включи `enable_php` в този или друг PDF клас (вижте и `docs/mvp/security/findings/P3.md`, P3-01, където е отбелязано същото).
- Нищо друго извън моите файлове не е необходимо за тези находки.

## Какво не е проверено / ограничения

- Не съм изпълнявал „жив“ `eval()`-payload срещу dompdf (P4-01) в тази сесия — находката и поправката са доказани чрез проследяване на кода (`PhpEvaluator.php:52`) и чрез успешно рендиране на PDF преди/след поправката; P3 независимо е изпълнил работещ PoC (вижте P3.md, P3-01).
- CSV/Excel formula injection тестовете (P4-03) покриват на живо, през реалните маршрути, всичките 8 експортни класа (виж по-горе) — всеки потвърден чрез temp запис/преименуване на съществуващ ред + връщане към оригинала.
- Пълна POST-заявка за `databackd.data.import.upload` през реалното ядро (с CSRF/сесия) не беше практично да се симулира от CLI скрипт извън `smoke.php` (което прави само GET); `mimes`-правилото е тествано директно през `Validator` с реални/фалшиви файлове (вж. находка P4-06), а самите страници на импорта (`index`, `mapping`, `template`) са минати през `docs/mvp/tools/smoke.php databackd.data. --ajax` без нов провал.
- Не съм прегледал в дълбочина `GoogleSheetsReader`/импорт по URL (P5) нито правата „кой може да импортира/експортира“ отвъд съществуващите `abort_403(in_array('client', user_roles()))` проверки (P2).
