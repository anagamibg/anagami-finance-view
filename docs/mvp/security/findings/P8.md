### P8-01 — Неавтентикиран „Emergency Backup Restore Tool“ в `public/backup-and-restore/` (критична)

**Доказателства (потвърдени):**
1. `GET https://databackd.com/backup-and-restore/` → **HTTP 200**, 34 869 B, `<title>Emergency Backup Restore Tool</title>` (това е `main-interface.php`; формата за вход `login-form.php` с текст „Only superadmin users…“ **не** се показва; има формуляр за `restore`). Сървърът задава бисквитка `restore_auth` без флагове `Secure`/`HttpOnly`/`SameSite`. Това е цялата заявка — не е изпращан POST, не е викан друг скрипт.
2. Причина в кода (идентичен локално в репото и на сървъра, `git ls-files public/backup-and-restore` — файловете са проследявани): `restore-backup.php:2051-2057`
   ```php
   // To be removed in next version
   $isLoggedIn = !isAuthenticated();
   if (!$isLoggedIn && !is_cli()) { include 'login-form.php'; exit; }
   ```
   Условието е обърнато: за **неавтентикиран** посетител `$isLoggedIn` става `true` → формата за вход се прескача и се зарежда пълният интерфейс; за автентикиран се показва формата за вход. Проверката по хост (`is_allowed_access()`, `:590-602`) се прилага само за CLI (`:2060`).
3. Останалите действия на инструмента са без токен/CSRF: `POST restore=1&backup_file=<път>` (`:2127-2148`) вика `restoreBackup()` (`:1591`), който **използва подадения път директно, ако файлът съществува** (`:1598-1599`, `basename()` е само резервен вариант) и изпълнява `.sql` срещу production базата (`restoreFromSql`), разархивира `.zip`/`.tar.gz` в корена на проекта (`extractZipToRoot`, `extractTarGzToRoot`) и трие `bootstrap/cache`; `POST clear_cache` изтрива файловете от `bootstrap/cache`.
4. Пет самостоятелни скрипта в `public/backup-and-restore/restore/` изобщо нямат проверка за вход (прочетено в кода): `server-diagnostic.php` (отпечатва хост/порт/име на базата/потребител и изпълнява `shell_exec` с `mysql -u… -p…`), `verify-restore.php` (`SHOW TABLES`), `debug-restore.php` (`CREATE TABLE`/`DROP TABLE` в production базата, `:156,:160`; `shell_exec("tail -n 20 …")` на лог файлове, `:178,:191`), `test-extraction.php` (`tar -xzf`, `rm -rf`, `:74,:97,:215`), `test-restore.php` (`tar -xzf` на `storage/app/backups/combined_backup_*.tar.gz` върху корена на проекта, `:38`, и `require_once restore-backup.php`). Те **не са заявявани** (част от тях пишат), достъпността им е заключение от факта, че същата директория се изпълнява от уеб сървъра (точка 1) и че root `.htaccess` не забранява `.php`.
5. Access log (`~/access-logs/databackd.com`, 2026-10-01 → 2026-10-28 09:10): 1 заявка към `backup-and-restore` (моята), 0 POST, 0 заявки към петте скрипта → няма следа за досегашна експлоатация. `Modules/` на сървъра е празна (модулът `BackupRestore` не е инсталиран) — инструментът е мъртъв код, но е публично достъпен.

**Сценарий за атака:** всеки неавтентикиран посетител отваря `/backup-and-restore/`, вижда състоянието на базата и списъка с бекъпи и изпраща `POST` с `backup_file`: (а) към съществуващ `.sql`/`.sql.gz`/`.zip` файл, достъпен за уеб потребителя (напр. резервно копие от функцията „database-backup-settings“ на AFV, или файл, качен през приложението в `public/user-uploads/…` — относителен път с `../`) — презаписване на цялата production база със стар/подправен дъмп (загуба на данни, изпълнение на произволен SQL) или разархивиране на подправен `.zip`/`.tar.gz` в корена на проекта → качване на PHP файл → RCE; (б) без файл — `clear_cache` (изтрива `bootstrap/cache/*`) и разузнаване (`server-diagnostic.php` издава име на база и потребител). Не е изпитвано на production (само четене); веригата (б) е потвърдена по код, веригата (а) — по код, но изисква подходящ файл на сървъра.

**Поправка (не е приложена — production е само за четене; репото е извън моите файлове):** виж „За S10“, т. 1.

**Статус:** за S10 — **спешно**.

### P8-03 — HTTP не се пренасочва към HTTPS; страницата за вход се сервира по HTTP; няма HSTS (средна)

- `curl -sI http://databackd.com/` → `302 Location: http://databackd.com/login` (пренасочва към **http**), `GET http://databackd.com/login` → **200** (11 914 B), `<form action="http://databackd.com/login">`; бисквитките `XSRF-TOKEN` и `worksuite_saas_session` по HTTP са **без `Secure`** (по HTTPS са със `Secure`).
- Причина: root `.htaccess` няма правило за HTTPS; `REDIRECT_HTTPS` в `.env` е `false` (`php artisan config:show app.redirect_https` → `false`) — и в кода (`AppServiceProvider.php:35,44`) тази настройка само принуждава схемата на генерираните URL адреси, **не** пренасочва заявките. `Strict-Transport-Security` липсва на всички проверени отговори.
- Сценарий: потребител, влязъл през `http://` (стар линк, лентата за адреси без схема, мрежов нападател), изпраща имейл и парола в чист текст; нападател в същата мрежа може да отнеме сесия/да подмени страницата (SSL stripping).
- Поправка: „За S10“, т. 3.

### P8-04 — Липсват защитни заглавия (средна)

На `https://databackd.com/`, `/login`, `/account/dashboard`, `/robots.txt` липсват: `Strict-Transport-Security`, `X-Frame-Options` (или `frame-ancestors`), `X-Content-Type-Options`, `Referrer-Policy`, `Content-Security-Policy(-Report-Only)`, `Permissions-Policy`. Налични: `X-Robots-Tag: noindex, nofollow` (`public/.htaccess`), `Cache-Control: no-cache, private` на `/login`. В приложението няма middleware за заглавия (само `FinApiGate` слага `X-Content-Type-Options` за API). Сценарий: clickjacking върху страницата за вход/интерфейса (липсва ограничение за вграждане в `<iframe>`), MIME sniffing, изтичане на URL чрез `Referer`. Поправка: „За S10“, т. 3.

### P8-12 — `GET`/`HEAD` към API маршрут дава HTTP 500 вместо 405 на production (ниска)
